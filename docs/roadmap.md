# 社会実装ロードマップ

> 防災サービスの価値は「作って終わり」ではなく **持続的に提供され、当事者と自治体に届き、データが更新され続ける** ことで初めて生まれる。本ドキュメントは、ハッカソン後の**普及・連携・継続**を1枚で示す（審査軸「サービスデザイン＝持続的に提供」に対応）。

## 現在地（正直な立ち位置）
- ✅ 東京都・国のオープンデータで**東京全域・要配慮者ファースト**の避難ナビが動作（Cloud Run 上のプロトタイプ）。
- ✅ インフラは Terraform 管理（Cloud Run / Vertex AI / BigQuery）で**再現可能**。LLM障害時も語句一致フォールバックで**止まらない**。
- 🟡 ライブデモは OSM/OSRM/Nominatim/PLATEAU 等の**公開・デモ依存**（本番配信には自前化が必要 → [issue #21](https://github.com/muroshima/Hinan-Navi-Tokyo/issues/21)）。
- 🟡 福祉避難所・ペット同行避難は**構造化オープンデータが存在せず**未統合（[#4](https://github.com/muroshima/Hinan-Navi-Tokyo/issues/4) / [#40](https://github.com/muroshima/Hinan-Navi-Tokyo/issues/40) で調査済み）。当事者ヒアリングは想定ペルソナ止まり（[docs/personas.md](personas.md)）。

## フェーズ別ロードマップ

| フェーズ | 目標 | 主な作業 | 対応issue |
|---|---|---|---|

## 3本の柱

### ① 自治体への配布・展開
- **配布形態**: (a) 自治体が自前ホスティングできる**OSSとして提供**（Apache-2.0・Terraformで再現可能）、(b) 都・区の防災ポータルへの**組み込み/リンク**、(c) 共有URL/QRで住民・支援者へ直接。
- **横展開**: データソースを差し替えれば他自治体に展開可能な設計（東京都OD前提の部分を抽象化）。

### ② 福祉部局・当事者団体との連携
- **データ連携**: 各区の**福祉避難所（二次避難所）・個別避難計画**は所在地非公開運用が多く、行政との連携でしか統合できない（[#4 調査](https://github.com/muroshima/Hinan-Navi-Tokyo/issues/4)）。福祉部局との協働を前提に設計。
- **当事者の声**: 障害者・高齢者・子育て・外国人支援団体への構造化ヒアリングを継続し、スコア要因・UI・マイ・タイムラインへ反映（[docs/personas.md](personas.md) のフィードバックループ）。

### ③ データ更新の継続
- **更新の自動化**: 東京都オープンデータの定期取得→`scripts/preprocess.py`→デプロイをCI/バッチ化し、避難所・トイレ・給水拠点等の**鮮度を維持**。
- **リアルタイム連携**: 避難所の**開設状況**（SIP4D / SOBO-WEB 等）の可否を調査し、平時データに動的情報を重ねる（[#36](https://github.com/muroshima/Hinan-Navi-Tokyo/issues/36)）。
- **データガバナンス**: 出典・ライセンス・取得日を [docs/DATA.md](DATA.md) と `metadata.json` で機械可読に保ち、更新履歴を追跡可能に。

## 持続可能性（コスト・体制）
- **コスト**: Cloud Run は min-instances=0 でアイドル無課金。LLMはレート制限＋キャッシュ＋予算アラート（[#30](https://github.com/muroshima/Hinan-Navi-Tokyo/issues/30) / [#69](https://github.com/muroshima/Hinan-Navi-Tokyo/issues/69)）でコストを抑制。重い地理処理は前処理に寄せてランタイムを軽量に保つ。
- **運用体制**: OSSとして公開し、自治体・シビックテック・当事者団体が継続改善に関与できる形を目指す。

## 一言で
**「東京で実証 → 公開基盤を整え → 1自治体と組んで実運用 → データ更新を自動化して全国へ」** ——
要配慮者の「行ける避難先」を、一度きりのデモでなく**持続的に届ける**ための道筋。
